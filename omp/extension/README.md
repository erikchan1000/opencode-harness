# Harness policy extension (omp)

An omp extension loaded through the `extensions:` list of `config.yml`
(`omp/install.sh` adds this directory; omp resolves it to `index.ts`).

## What it enforces

- **MCP scoping** (`mcp-scope.ts`): subagents may only call the scoped MCP
  servers `policy.json` allows for their agent name, mirroring the per-agent
  `<server>_*: allow` rules in `opencode.jsonc`. The `tool_call` block is the
  guarantee; `session_start` / `before_agent_start` also hide denied tools
  (best effort). The main session is never restricted, so write-capable work
  (Stripe, Cloudflare, Telnyx, ...) stays in the watched session.
  - Fail closed: a subagent not listed in `policy.json` (omp built-ins `task`,
    `explore`, `/tan` clones, the `advisor`) gets no scoped server.
  - Fail open: an MCP server not listed in `policy.mcp.servers` (no global
    deny in `opencode.jsonc`) is visible to every agent, as in opencode.
- **Spawn guard** (`spawn-policy.ts`): `harness-impl`, `harness-test` and
  `harness-debug` may only be spawned by `harness-pipeline`; the main session
  and other subagents are refused (`before_subagent_spawn`).

## Data

`policy.json` is GENERATED by `omp/build.py` (via `omp/policy.py`) from
`opencode.jsonc`, `agents/*.md` and the omp `spawns:` lists. Regenerate with
`python3 omp/build.py`; never edit it. A missing or malformed file fails
extension load (`parsePolicy`). omp then starts the session WITHOUT the policy
(no MCP scoping, no spawn guard) and shows a single "Failed to load extension"
warning (subagent sessions only log it). Treat that warning as a stop. The
extension cannot log this itself: the import throws before any code of ours runs.

## Limits

- MCP server `instructions` text still reaches every subagent's system prompt;
  removing it needs an omp core patch. Only the tools and the calls are removed.
- A project `.omp/config.yml` `extensions:` list REPLACES the user list, which
  would drop this extension inside that project.
- The TypeScript is not typechecked against the fork (no tsconfig here).

## Result triage

`result-triage.ts` condenses large settled `task` results before they enter the
orchestrator's context (`async_result` event). **Default OFF.** It calls the
cheap `@smol` model directly (not an ephemeral turn, which would re-send the
parent's whole context per child); see the module header for the rationale.

Enable in `<agentDir>/harness-policy.json` (user-owned; the installer never
writes it):

```json
{ "resultTriage": { "enabled": true } }
```

Keys (defaults): `enabled` (false), `thresholdChars` (6000), `model`
(`"@smol"`), `maxDigestChars` (2500), `timeoutMs` (20000, must be < 30000),
`statuses` (`["completed"]`), `jobTypes` (`["task"]`; add `"bash"`/`"eval"` to
triage those). The digest prompt is `result-triage.prompt.md`.

Failure behavior: a missing file or key means off. An invalid config is logged
once (and notified in the UI) and results are delivered unchanged. Any digest
failure (unresolved model, no API key, timeout, error, empty or longer digest)
logs a warning and delivers the original result. Results are never suppressed;
core always keeps the status header and the `agent://` / `proc://` pointer
(the digest footer carries no pointer of its own). At most 4 digests
run concurrently.
